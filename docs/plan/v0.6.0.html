Plan v0.6.0

v0.6.0 builds the commute tool. It turns 8 weeks of measured bus arrivals into departure patterns, works out ride time between two stops, and adds a /commute page that says which bus to catch, how long the ride takes and how late it runs. Five features, each one issue and one PR, merge into release/v0.6.0.

Status: Draft for the owner's approval. Spec: v0.6.0. Grill record: commute tool.

Decisions

Each card is a decision with real options. The chosen option is marked and has a heavy border. Cards run in number order.

0003. Ship commute data as route files built daily

  • ChosenOne file per bus route and one stop list, built by the daily job from the timetable calendar
  • ConsideredOne file per stop, built by the daily job
  • ConsideredA new arrivals column for the service day type, which makes arrivals v3

WhyA visit loads the stop list and one route file, about 260 KB, and the build needs no change to graded data and no regrade.

Grill answers

A Q is a question from the grill record. Each card is an answer that chose between real options. Q9 is covered by ADR-0003.

Q1. Which lines the commute tool covers

  • ChosenBus only. The tool says rail is not covered yet.
  • ConsideredBus and rail, rail flagged
  • ConsideredBus and rail, no flag

WhyRail trip ids are wrong on split-service days while the rail matcher is off, so a rail answer could not be trusted.

Grill record, Q1

Q2. Which stop times feed the answer

  • ChosenMeasured only. Estimated and missing stops are left out.
  • ConsideredInclude estimates

WhyThe answer should rest on times a bus was seen at the stop, so rows with source interpolated or none do not count.

Grill record, Q2

Q3. Which days an answer is built from

  • ChosenLast 8 weeks, which is the 56 service days that end with the latest graded day.
  • ConsideredEvery day collected
  • ConsideredCurrent timetable only

WhyThe owner picked the 8-week window, and a fixed count of days makes the boundary testable.

Grill record, Q3

Q4. Where the commute screen lives

  • ChosenA new /commute page, linked from the home page and each bus line page.
  • ConsideredOn the home page
  • ConsideredInside each line page

WhyThe owner picked a page of its own, and the spec tests the links from the home page and from every bus line page.

Grill record, Q4

Q5. Below how many observed days a stop says not enough data

  • Chosen8 days. The page says how many days an answer rests on.
  • Considered15 days
  • Considered5 days

WhyAn answer under 8 days would show a number the data cannot carry, so it reads "not enough data" instead.

Grill record, Q5

Q6. How holidays count in the 8-week window

  • ChosenBy the timetable Metro ran that day.
  • ConsideredLeave holidays out
  • ConsideredBy calendar day

WhyA Thursday holiday that runs Sunday service belongs with Sunday departures, because those are the buses that ran.

Grill record, Q6

Q7. How the nearest stop is found

  • ChosenIn the browser only. The location never leaves the phone, and a denied prompt falls back to search.
  • ConsideredDrop nearest stop

WhyNo request from the page carries the rider's latitude or longitude, and a rider who says no still gets stop search with no error.

Grill record, Q7

Q8. Whether the 9 in 10 level can change

  • ChosenFixed at 9 in 10.
  • ConsideredLet the rider pick 3 in 4, 9 in 10 or 19 in 20

WhyOne fixed level keeps the answer sentence and the Arrive by boundary simple to test.

Grill record, Q8

Q10. How the build finds the timetable that ran on a date

  • ChosenIt looks the date up in Metro's stored GTFS calendar.
  • ConsideredAdd it to graded arrivals as a new column, which makes arrivals v3

WhyGraded arrivals stay v2, so the build changes no stored data and no day is regraded.

Grill record, Q10

Risks

  • Ride time needs same-trip pairs. A spread of times at each stop does not give the spread of A to B ride times. The route file may need each day's time at each stop, not quantiles alone, which can make files several times larger than ADR-0003 estimated. Feature 1 measures the size of both layouts on the VM. If the larger layout passes about 300 KB gzipped for the busiest route, I ask the owner before building.
  • A bus service runs on more than one day type. Then a date has no single day type and S1 fails. Feature 1 counts such services first. If any exist, I ask the owner how to classify them.
  • A timetable change starts new patterns. A departure moved by one minute has under 8 days of data, so it reads "not enough data" for up to 8 weeks. The page then says so for that departure. Matching near start times across versions is not in this version.
  • The daily job slows or runs out of memory. The pattern build groups about 49 million rows. Feature 1 runs it on 56 real days in the VM and reports time and peak memory before it merges. The daily job's timeout is 3 hours, so a slow build delays the site but does not fail the run.
  • The site's daily upload to R2 grows. It goes from about 3.8 MB to about 10 to 11 MB gzipped. R2 charges nothing for egress and little for writes at this size, so the bill stays near $1.50 a month.
  • An agent downloads data to a laptop to check a commute. The egress guard refuses raw files, and CLAUDE.md forbids it. C23 runs on the VM.
  • Location denial behaves differently in Playwright than on a phone. C11 then needs a manual check on a phone, which I add to the owner's test in C24.
