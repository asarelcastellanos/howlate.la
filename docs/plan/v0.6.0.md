# Plan v0.6.0

Spec: [v0.6.0](../spec/v0.6.0.md). Grill record: [commute tool](../grill/2026-11-24-commute-tool.md). Decision: [ADR-0003](../adr/0003-ship-commute-data-as-route-files-built-daily.md).

Each feature is one issue and one PR. Branches follow this repo's rule in `CLAUDE.md`. They are named `v0.6.0/<short-name>` and merge into `release/v0.6.0`.

## What it adds

| Part | What it is | Claims |
|---|---|---|
| Departure patterns | The daily job groups 8 weeks of measured bus arrivals by route, direction, day type and start time, and ships one commute file per route and a stop list | C1 to C6 |
| Ride time | Ride time from stop A to stop B, from the same trip on the same day | C7, C8 |
| Stop search and nearest stop | Find a stop by name, or the nearest one on the phone | C9 to C12 |
| Commute screen | The `/commute` page with Leave at and Arrive by, the answer sentence, and the address that holds the commute | C13 to C22 |
| Release | Five commutes checked against arrival rows, the phone test, and the review package | C23 to C25 |

## Build order

1. **Departure patterns** (#34). Branch `v0.6.0/patterns`. Claims C1 to C6. Depends on nothing. Its first step runs a script on the backfill VM that counts, for 56 recent days, the bus services that ran and the day type each one runs on. That settles S1 before any build code. The same script measures the size of a route file for the busiest and an average route, which settles S3.
2. **Ride time** (#35). Branch `v0.6.0/ride-time`. Claims C7, C8. Depends on 1, because it reads the pattern files.
3. **Stop search and nearest stop** (#36). Branch `v0.6.0/stop-search`. Claims C9 to C12. Depends on 1, because it reads the stop list. It runs beside 2.
4. **Commute screen** (#37). Branch `v0.6.0/commute-screen`. Claims C13 to C22. Depends on 2 and 3.
5. **Release** (#38). Branch `v0.6.0/release-prep`. Claims C23 to C25. Depends on every feature above. C24 is the owner's test with three people.

## Risks

- **Ride time needs same-trip pairs.** A spread of times at each stop does not give the spread of A to B ride times. The route file may need each day's time at each stop, not quantiles alone, which can make files several times larger than ADR-0003 estimated. Feature 1 measures the size of both layouts on the VM. If the larger layout passes about 300 KB gzipped for the busiest route, I ask the owner before building.
- **A bus service runs on more than one day type.** Then a date has no single day type and S1 fails. Feature 1 counts such services first. If any exist, I ask the owner how to classify them.
- **A timetable change starts new patterns.** A departure moved by one minute has under 8 days of data, so it reads "not enough data" for up to 8 weeks. The page then says so for that departure. Matching near start times across versions is not in this version.
- **The daily job slows or runs out of memory.** The pattern build groups about 49 million rows. Feature 1 runs it on 56 real days in the VM and reports time and peak memory before it merges. The daily job's timeout is 3 hours, so a slow build delays the site but does not fail the run.
- **The site's daily upload to R2 grows.** It goes from about 3.8 MB to about 10 to 11 MB gzipped. R2 charges nothing for egress and little for writes at this size, so the bill stays near $1.50 a month.
- **An agent downloads data to a laptop to check a commute.** The egress guard refuses raw files, and `CLAUDE.md` forbids it. C23 runs on the VM.
- **Location denial behaves differently in Playwright than on a phone.** C11 then needs a manual check on a phone, which I add to the owner's test in C24.
