# Spec v0.6.0

Status: approved 2026-11-24. Grill record: [commute tool](../grill/2026-11-24-commute-tool.md). Tests carried from [the release plan](../release-plan.md), section "0.6.0 Commute tool".

## Goal

After this version a bus rider can open howlate.la/commute, pick a route, two stops and a time, and read which bus to catch, how long the ride takes and how late it usually runs. The answer comes from the last 8 weeks of measured arrivals, and a shared link shows the same answer.

## How to read a claim

Each claim is one testable sentence. "I said" quotes the grill record, as `Q<n>, <answer>` where the owner picked an option. "Release plan" in that line quotes a test the owner wrote in `docs/release-plan.md`, which the grill took in scope. "Proof" says how the claim is shown to work. "Assumes" lists the assumption IDs the claim depends on. QA proves each claim in a real session and posts the evidence in one comment on the issue PR, with `gh pr comment --attach`. QA writes no evidence folder in the repo.

QA never downloads graded or raw data to a laptop. Checks against arrival rows run on the backfill VM with `backfill-vm.sh --script`, as `CLAUDE.md` requires.

## F0 Departure patterns (#34)

**C1.** The daily job shall key each bus trip by route, direction, day type and scheduled start time, so that trips from two timetable versions with the same key form one departure pattern.
- I said: Release plan, "A fixture with two timetable versions maps the weekday 7:42 departure from both versions to one pattern."
- Proof: Unit test, because this is a data invariant. A fixture with two timetable versions, whose trip ids differ, holds a weekday 7:42 departure in each. The test expects one pattern holding the days from both.
- Assumes: S2, S6

**C2.** The daily job shall give each service date the day type of the timetable Metro ran that day, read from the stored GTFS calendar.
- I said: Q6, "By timetable run", and Q10, "Look it up from GTFS".
- Proof: Unit test, because the cases are many. A fixture calendar holds a plain weekday, a Saturday, a Sunday, and a Thursday holiday that runs Sunday service by a `calendar_dates` exception. The test expects weekday, Saturday, Sunday and Sunday.
- Assumes: S1

**C3.** A bus trip that runs past midnight shall belong to the service date and day type on which it started.
- I said: Release plan, "a trip after midnight belongs to the day it started."
- Proof: Unit test, because this is a boundary. A fixture Friday trip starts at 23:50 and reaches its last stop at 00:20 on Saturday. The test expects every stop of it under Friday's weekday pattern.

**C4.** Commute answers shall use only measured bus arrivals, and leave out estimated and missing stops.
- I said: Q1, "Bus only", and Q2, "Measured only".
- Proof: Unit test, because this is a data invariant. A fixture pattern holds measured, `interpolated` and `none` rows and one rail trip. The test expects only the measured bus rows in the result.

**C5.** Commute answers shall use the 56 service days that end with the latest graded day.
- I said: Q3, "Last 8 weeks".
- Proof: Unit test at the boundary. With the latest graded day 2026-11-23, a row from 2026-09-29 counts and a row from 2026-09-28 does not.

**C6.** The daily job shall write one commute file per bus route and one bus stop list into each site run, and copy them to R2 with the rest of the run.
- I said: Q9, "One file per route + stop list".
- Proof: QA reads `gs://howlate-derived/site/current.json` after a daily run, lists the run folder, and shows one commute file per bus line in `index.json`, the stop list, and the same files at `https://data.howlate.la`. QA states the gzipped size of the stop list and of the largest route file.
- Assumes: S3, S4

## F1 Ride time (#35)

**C7.** Ride time from stop A to stop B shall come from the actual times at A and at B on the same trip and day only.
- I said: Release plan, "Ride time from A to B uses arrivals from the same trip only."
- Proof: Unit test, because this is a data invariant. A fixture day holds two trips of one pattern on the same day, with hand-worked times at A and B. The test expects two ride times, each from one trip, and none mixed.

**C8.** The commute tool shall refuse a "to" stop that comes before the "from" stop in the chosen direction.
- I said: Release plan, "A 'to' stop that comes before the 'from' stop on the route is rejected."
- Proof: Unit test on the pattern lookup, and QA on the page, which shows that the earlier stop cannot be chosen as "to".

## F2 Stop search and nearest stop (#36)

**C9.** A rider shall find a bus stop by typing part of its name.
- I said: Release plan, "Add stop search by name".
- Proof: QA types "Wilshire / Vermont" on `/commute` and shows the stop in the results.
- Assumes: S3

**C10.** The commute page shall find the nearest bus stop on the phone, and no request from the page shall carry the rider's location.
- I said: Q7, "In the browser only".
- Proof: QA grants a fixed location in Playwright, shows the nearest stop picked, and shows the network log of the visit with no request that holds the latitude or longitude.
- Assumes: S5

**C11.** When location access is denied, the commute page shall offer stop search and show no error.
- I said: Q7, "Denied falls back to search", and Release plan, "If location access is denied, the tool falls back to search."
- Proof: QA denies the location permission in Playwright and shows the search box focused and no console error.
- Assumes: S5

**C12.** A stop served in only one direction of a route shall not be offered in the other direction.
- I said: Release plan, "A stop served in only one direction cannot be picked the wrong way."
- Proof: QA picks a one-direction stop on a real route and shows it missing from the other direction's list.

## F3 Commute screen (#37)

**C13.** The commute page shall live at `/commute`, with links to it from the home page and from every bus line page.
- I said: Q4, "New /commute page".
- Proof: QA opens the home page and one bus line page and follows each link to `/commute`.

**C14.** With "Leave at", the commute page shall pick the first scheduled departure from stop A at or after the chosen time.
- I said: Release plan, "'Leave at 8:00' picks the first scheduled departure from A at or after 8:00."
- Proof: Unit test at the boundary. With departures at 7:59, 8:00 and 8:07, "Leave at 8:00" picks 8:00, and "Leave at 8:01" picks 8:07.

**C15.** With "Arrive by", the commute page shall pick the latest departure whose arrival at stop B is at or before the chosen time on 9 of every 10 observed days.
- I said: Q8, "Fixed at 9 in 10", and Release plan, "'Arrive by 9:00' picks the latest departure whose 9-in-10 arrival is at or before 9:00. Test the boundary minute."
- Proof: Unit test at the boundary. One departure's 9-in-10 arrival at B is 9:00 and a later one's is 9:01. "Arrive by 9:00" picks the first, and "Arrive by 9:01" picks the second.

**C16.** The answer shall say how late the bus usually is, how bad it gets, which bus to catch and how long the ride takes, as a plain sentence before any chart.
- I said: Release plan, "The answer appears first as a plain sentence, and the chart comes after it."
- Proof: QA screenshots an answer for route 720 and shows the sentence above the chart.

**C17.** A screen reader shall read the answer sentence when the answer changes.
- I said: Release plan, "A screen reader reads the answer sentence."
- Proof: QA reads the accessibility tree in Playwright and shows the sentence in a live region.

**C18.** An answer resting on fewer than 8 observed days shall read "not enough data", and every other answer shall say how many days it rests on.
- I said: Q5, "8 days".
- Proof: Unit test at the boundary, because a wrong count shows a number the data cannot carry. A pattern with 7 days returns "not enough data", and one with 8 returns an answer that says 8 days. QA then shows both on the page.

**C19.** Weekday, Saturday and Sunday answers shall each use their own departure patterns.
- I said: Release plan, "Weekday, Saturday and Sunday each use their own patterns".
- Proof: Unit test, because the cases are many. A fixture route has a 7:42 departure on each day type with different times. Each day type returns its own.

**C20.** The commute shall live in the page address, so a shared link opens the same route, stops, mode and time with the same answer.
- I said: Release plan, "The commute lives in the URL, so a shared link shows the same answer."
- Proof: QA sets up a commute, copies the address into a fresh browser context, and shows the same answer.

**C21.** Switching between "Leave at" and "Arrive by" shall keep the chosen route and stops.
- I said: Release plan, "Switching between Leave at and Arrive by keeps the chosen stops."
- Proof: QA switches the mode on a set commute and shows the same stops.

**C22.** The commute page shall say that rail lines are not covered yet.
- I said: Q1, "The tool says rail is not covered yet."
- Proof: QA screenshots the note on `/commute`.

## Amendments after approval

The owner made these decisions on 2026-11-24, after approving the spec, when the sizing runs on #34 measured the files. Each one changes how a claim above is read. The claims keep their original wording.

**A1, on C6.** The daily job writes one commute file per bus route, direction and day type, not one per route. Each day's time at each stop is rounded to 10 seconds and coded as the change from the stop before. A file may be up to 450 KB gzipped, and the build fails the day when one passes it.
- I said: round 4 Q11, "Split files smaller", Q12, "Yes, 10 seconds", and Q13, "Allow up to 450 KB".
- Effect: C6's proof lists one file per bus line, direction and day type in the run folder. QA states the largest file's gzipped size, which must be 450 KB or less. [ADR-0004](../adr/0004-split-commute-files-by-direction-and-day-type.md) replaces ADR-0003.

**A2, on C7.** Ride time is exact to 10 seconds, not to the second.
- I said: round 4 Q12, "Yes, 10 seconds".
- Effect: C7's test expects ride times rounded to 10 seconds.

## Spec assumptions

| ID | Assumption | For | Against |
|----|------------|-----|---------|
| S1 | The stored GTFS for each date names the services that ran, through `calendar.txt` and `calendar_dates.txt`, and each bus service that ran runs on one day type only. Checked, `gtfs.py:202-228`, and `commute_sizing.py` on the backfill VM (#34). 91 bus services ran in the 56 days ending 2026-11-23, none on more than one day type, and all 56 dates resolved to one. | The build can then name a date's day type from its active services without a new column. | A service that runs every day of the week, or a holiday service named for no day type, has no single day type. The first builder must count such services on the VM. |
| S2 | Graded arrivals carry `route_id`, `direction_id`, `trip_id`, `stop_sequence`, `scheduled_time`, `actual_time`, `source` and `is_origin`. Checked, `arrivals.py:823-830`, scout report 2026-11-24. | A pattern and a ride time can be built from the rows the daily job already fetches. | The trip start time is not a column. The build takes it from the trip's first scheduled stop, as `trips.scheduled_start` does at `arrivals.py:794-796`. |
| S3 | Under A1, a commute file is 27,557 bytes gzipped at the median and 411,809 at the largest, and the stop list is 192,639 bytes. Checked, `commute_sizing.py` run `20261125T051309Z` on the backfill VM, #34. The first estimate of 60 KB and 130 KB per route was wrong, which A1 records. | A visit loads about 220 KB for the median file. | The sizes measure the script's JSON array layout, and the build may store stop ids or keys differently. |
| S4 | The daily job can read 56 days of arrivals within its 16 GiB, with DuckDB capped at 8 GB, and stays near its current 5 to 7 minutes. Checked, `daily.sh:291-318` and `gcloud run jobs executions list`. | It already reads all 98 graded days, about 0.8 GB of parquet, on every run. | The pattern build adds a group by trip and stop over about 49 million rows that no run has done yet. |
| S5 | Playwright can set a fixed location with the `geolocation` and `permissions: ['geolocation']` context options, and a context without that permission denies the page's location request. Checked in part, https://playwright.dev/docs/emulation and the `grantPermissions` and `clearPermissions` sections of https://playwright.dev/docs/api/class-browsercontext, read 2026-11-24. The docs do not say what a denied page receives, so the denial half is Unchecked. | C10 and C11 can then be proven with no device. | If a context without the permission prompts or hangs instead of denying, C11 needs a manual check on a phone. |
| S6 | Two trips from different timetable versions with the same route, direction, day type and start time are the same bus run to a rider. Unchecked. | The release plan's pattern key rests on it. | A timetable change that moves a departure by one minute makes a new pattern with less than 8 days, so it reads "not enough data" for up to 8 weeks. |
| S7 | A backfill VM run over five recent days costs under $0.10. Checked, the v0.5.2 four-day regrade on 2026-11-24 took about 10 minutes on a Spot e2-standard-8, and days under 30 days old pay no retrieval fee. | C23 needs no budget question. | Days older than 30 days pay Coldline retrieval at $0.02 per GB, about 1.2 GB each. |
